# Git vs SVN — ответы на вопросы

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

В Git ветка — это не копия файлов, а **обычный текстовый файл размером около 41 байта**,
в котором лежит SHA-хеш коммита, на который ветка указывает (`.git/refs/heads/<имя>`).
Создание ветки = запись одной ссылки: ноль копирования данных, операция мгновенная
и полностью локальная. Переключение между ветками — это перемещение указателя `HEAD`
и обновление рабочей директории.

В SVN ветка исторически реализована как **копия директории внутри репозитория**
(`svn copy trunk branches/my-feature`). Даже с «дешёвым копированием» на стороне сервера
операция выполняется **на сервере и по сети**, попадает в общую нумерацию ревизий
и требует отдельного `svn switch` либо новой рабочей копии на диске. Вдобавок SVN долго
не умел отслеживать историю слияний — свойство `svn:mergeinfo` появилось только
в версии 1.5, — поэтому повторный merge одной и той же ветки приводил к конфликтам,
и разработчики старались веток не плодить.

**Итог:** в Git создать ветку под каждую задачу — рядовая операция, которую делают
по несколько раз в день. В SVN создание ветки — событие, к которому подходят осознанно.

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

**Нет, нельзя.**

SVN — **централизованная** система контроля версий: единственная копия истории и
единственный сквозной счётчик ревизий живут на сервере. Коммит в SVN — это атомарная
транзакция на сервере, создающая новую глобальную ревизию (r1, r2, r3, ...). Клиент
физически не может создать ревизию сам: у него нет ни истории целиком, ни права выдать
следующий номер. Локально в рабочей копии хранится только закешированная BASE-ревизия,
поэтому офлайн доступны лишь `svn status`, `svn diff` и `svn revert` относительно неё.

В Git всё наоборот: полная история лежит в локальном каталоге `.git`, а коммит
идентифицируется SHA-хешем своего содержимого, а не порядковым номером с сервера.
Поэтому коммитить, создавать ветки, мержить, смотреть `log` и `diff` можно полностью
офлайн — в самолёте или поезде. Сеть нужна только для синхронизации с другими
разработчиками: `push`, `fetch`, `pull`.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

- **Большие бинарные файлы.** Геймдев, CAD, видеопродакшен, дизайн-ассеты: Git хранит
  полную историю у каждого разработчика, и репозиторий с гигабайтами бинарников
  распухает до неработоспособного состояния (бинарники не сжимаются дельтами).
  SVN выкачивает только текущую ревизию. В Git для этого нужен внешний костыль — Git LFS.

- **Частичная выгрузка (partial checkout).** В SVN можно выгрузить одну подпапку
  большого монорепозитория и работать только с ней. Git по умолчанию требует
  склонировать репозиторий целиком со всей историей.

- **Гранулярные права доступа.** SVN умеет раздавать права на уровне отдельных каталогов:
  подрядчик видит только свой модуль. В Git права выдаются только на репозиторий целиком —
  либо есть доступ ко всему, либо ни к чему.

- **Централизованный контроль и аудит.** Вся история в одном месте под управлением
  администратора; разработчик не может унести с собой полную копию репозитория.
  Это требование часто встречается в госсекторе, банках и на предприятиях
  с режимом коммерческой тайны.

- **Legacy-инфраструктура.** Если вокруг SVN за 15 лет выстроены процессы, регламенты,
  системы сборки и интеграции, миграция огромного проекта обходится дороже, чем
  поддержка существующей системы.

- **Линейная нумерация ревизий.** Номер вида `r1274` понятнее в отчётах, регламентах
  и разговоре, чем SHA-хеш `e042933`, и сразу даёт представление о хронологии.
